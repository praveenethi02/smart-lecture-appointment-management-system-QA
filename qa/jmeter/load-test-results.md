# Performance Testing – JMeter Load Test

## Test configuration

| Item | Value |
|---|---|
| Tool | Apache JMeter 5.6.3 (Java 25), non-GUI mode |
| Test plan | `qa/jmeter/lecturers-load.jmx` |
| Endpoint | `GET http://localhost:5000/api/lecturers` (public lecturer directory) |
| Thread Group | 50 users, ramp-up 10 s, loop count 5 → **250 requests** |
| Assertions | HTTP status = 200; response body contains `"success":true` |
| Listeners | Summary Report, Aggregate Report, Response Time Graph, View Results Tree (errors only) + HTML dashboard |
| Environment | Windows 11, Node.js 24, local MongoDB 9.0, backend and JMeter on the same machine |
| Command | `jmeter -n -t qa/jmeter/lecturers-load.jmx -l qa/jmeter/results/lecturers-load.jtl -e -o qa/jmeter/html-report` |

## Analysis

- All 250 requests returned HTTP 200 with a valid body. No errors appeared under 50 concurrent users.
- Response times stayed very low (average 6 ms, 95% under 8 ms). The max of 72 ms happened during the first second while connections were warming up.
- Throughput (~26 req/s) is limited by the test design (50 users × 5 loops over about 10 s), not by the server. The server was not saturated.
- **Limitation:** the backend, database and JMeter all ran on one laptop, and the database is small (4 lecturers). Production results would differ, so a larger dataset and a separate load-generator machine would be needed for a realistic capacity test.
- `POST /api/auth/login` was **not** load-tested on purpose: it is protected by a rate limiter (100 requests / 15 min per IP) and returns `429 Too Many Requests` after the limit. This behaviour is shown separately as a security control (see `qa/security/owasp-findings.md`, screenshot [SEC-05](../security/screenshots/SEC-05-rate-limit-429.png)).
